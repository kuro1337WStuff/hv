# 120 · Do calibration and IRQ0 see the same elapsed time?

**Yes on the shared host platform.** One supplied nanosecond timestamp advances the existing IRQ0-producing PIT channel 0 and the gated calibration channel 2. The PIC pair is the same one that handles serial IRQ4 and ACPI SCI. Port transactions and interrupt acknowledgments do not supply time. The cycle count is a declared **virtual** 2.5 GHz, not a host frequency measurement.

| Elapsed ns | Virtual cycles | PIT pulses | Observation |
|---:|---:|---:|---|
| 4,201 | 10,502 | 5 | Channel 2 held `1202h` with its gate closed. Channel 0 had already latched a masked IRQ0. UART got vector `34h`; unmasking IRQ0 let `30h` preempt it without time advancing. |
| 8,401 | 21,002 | 10 | Channel 2 counted down to `11FDh`; a pending high-byte read reflected the live count. A new IRQ0 could not preempt itself; the specific EOI allowed exactly the next `30h` grant. |
| 9,300 | 23,250 | 11 | Only the `1401h` selector-only copy advanced, to `11FCh`. The `3401h` S5 copy rejected the advance and channel-2 accesses; its full state stayed unchanged at 8,401 ns. |

Bulk advancement and 317 ns subdivisions agreed at both comparison points. Independent integer arithmetic reproduced `floor(ns × 1193182 / 10⁹)` PIT pulses and `floor(ns × 2500000000 / 10⁹)` virtual cycles. Repeating a timestamp did nothing; moving backwards by 1 ns was refused even within the same PIT pulse. At `7378697629483820646` ns the running platform reached `UINT64_MAX` cycles; the next ns was refused without modifying state. The older isolated cycle fixture still wraps by design.

**Reproduce:** compile and run `lab/tests/platform_clock_test.c` on [feature PR #152](https://github.com/kuro1337WStuff/hv/pull/152) with x64 MSVC `/O2 /std:c11 /W4 /WX` or GCC `-std=c11 -O2 -Wall -Wextra -Werror`. Local MSVC and the [hosted Ubuntu PIC job](https://github.com/kuro1337WStuff/hv/actions/runs/45734811363/job/139625365921) emitted the same two result lines on tree `0979b99dc6f59d2828c4244751865ccb872a403b` (hosted PR merge `cd6429e20c0102c35402d7c31ee018b08cd018f4`). MSVC also passed `pit_shared_test`, `pit_cycle_clock_test`, and the prior `platform_s5_test` with all eight shutdown trace lines unchanged. Feature integration: `c93758cb`.

No `RDTSC`, physical timing, guest interrupt delivery, Linux clock selection or VM boot was tested.

# 116 · Can the timer, ACPI event and serial port share an interrupt controller?

**Yes, at the modeled controller boundary.** With three simultaneous requests, the PIC pair accepted the timer (`30h`), then the ACPI system control interrupt (`39h`), then COM1 (`34h`) once the ACPI source was cleared and its service acknowledged. [115](115.md) had no slave route; [098](098.md) had no competing interrupts. Here the three sources share one set of mask and in-service registers. No CPU or guest handler received a vector.

| Stimulus | Observed result |
|---|---|
| Multiple PIT and UART rises behind masks, with the ACPI source asserted | Edge storage `11h` (IRQ0 and IRQ4). Unmasking slave IR1 added cascade bit `04h` to the master's pending inputs, not to edge storage. With the master open, eligible bits were `15h`. |
| Clear the PM1a cause during SCI service | SCI level fell; master/slave in-service registers stayed `04h/02h`. Clearing the source is not an EOI. Clearing it **before** acceptance instead left no SCI request. |
| Persistent SCI, slave EOI first | Master/slave service `04h/00h`: SCI pending, not eligible. Master EOI made it eligible again without a new PM1 event. |
| Persistent SCI, master EOI first, UART pending | Service `00h/02h`: SCI could not recur, but the now-free master accepted IRQ4. Clearing slave service then allowed SCI to interrupt the UART. |
| Timer interrupted that nested SCI | Master/slave service `15h/02h`; another timer edge was pending but could not interrupt itself. Final service registers `00h/00h`. |

**Verification:** x64 MSVC `/O2 /std:c11 /W4 /WX` built and ran `shared_sci_pic_test`, `pit_uart_pic_test` and `power_sci_test` from tree `cc3b46ba2fc3381b771f7b44ecb1c91add4d9ad2`. The existing two-edge transcript was unchanged. An independent check ranked unmasked requests by line number against the highest active master priority. It agreed on the next eligible choice at all 25 named states and matched all 11 accepted vectors. The first source revision (`826489cd`) did **not** compile under `/WX`: C5287 flagged a bitwise OR across two enum types. The final revision tests timer and cascade eligibility separately; no warning was disabled.

**Cross-platform result:** [GitHub-hosted GCC](https://github.com/kuro1337WStuff/hv/actions/runs/45732682333/job/139618306313) executed PR merge `cebcfca8dcc4a46a38a63bb54cb593d310832901` on that same tree. [PR #142](https://github.com/kuro1337WStuff/hv/pull/142) landed on `feature/l1-handoff` at `a8563a8c`; `main` firmware did not change.

**Reproduce:** from [the implementation PR](https://github.com/kuro1337WStuff/hv/pull/142), build each `lab/tests/<name>.c` separately with the flags above, or run the shared control with `gcc -std=c11 -O2 -Wall -Wextra -Werror lab/tests/shared_sci_pic_test.c -o shared-sci && ./shared-sci`. The scope is an initialized, fixed-priority pair. The cascade is sampled from an enabled PM1a level, not a complete model of INTA timing or spurious IRQs. The [ACPI PM1 status contract](https://uefi.org/specs/ACPI/6.5/04_ACPI_Hardware_Specification.html#pm1-status-registers) and [Linux specific EOI sequence](https://github.com/gregkh/linux/blob/v6.18.60/arch/x86/kernel/i8259.c#L158-L199) are the reference points.

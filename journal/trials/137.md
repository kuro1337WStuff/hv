# 137 · Can discovery distinguish an empty optical drive from a missing target?

**Yes in the host model.** Standard INQUIRY described the attached drive, not the disc. Removing the authored medium left the 36 identity bytes unchanged; removing the target itself caused inquiry to fail. No ISO, VM or physical optical device was needed.

| Target state | Standard INQUIRY | TEST UNIT READY | READ CAPACITY(10) | READ(10), one sector at LBA 2 |
|---|---|---|---|---|
| Attached, three sectors | 36 bytes, type 5, removable | Accepted, 0 bytes | 8 bytes: last LBA 2, 2,048 bytes/block | 2,048 known bytes; one backing lookup |
| Same drive, empty | Identical 36 bytes | Refused, 0 bytes | Refused, 0 bytes | Refused, no lookup |
| Absent | Refused, 0 bytes | Refused, 0 bytes | Refused, 0 bytes | Refused, no lookup |

The accepted inquiry prefix lengths were 0, 13, 36 and 36 for allocations 0, 13, 36 and 255. A caller offering only 12 bytes for the 13-byte reply got a refusal, not a partial write. Guards and untransferred bytes stayed unchanged. Inquiry, readiness and capacity did not touch the backing. An explicitly zero-count READ(10) on an attached empty target succeeded without returning data; it is **not** evidence of a readable disc.

**Scope:** the [pinned EDK II inquiry builder](https://github.com/tianocore/edk2/blob/556dcfb466e9f05affeaff881d738807f8156d3c/MdePkg/Library/UefiScsiLib/UefiScsiLib.c#L297-L316) requests a six-byte command and observes the returned transfer length. The [firmware parser](https://github.com/tianocore/edk2/blob/556dcfb466e9f05affeaff881d738807f8156d3c/MdeModulePkg/Bus/Scsi/ScsiDiskDxe/ScsiDisk.c#L3517-L3523) reads the removable bit. The test implements that plain profile with an authored identity; it does not forward a hardware identity. `accepted` is not a SCSI target-status byte. The fixture cannot yet tell firmware *why* a command failed, and it provides no sense records, AHCI transport, Windows driver binding or post-firmware guest read.

**Repeat:** compile [the test](https://github.com/kuro1337WStuff/hv/blob/c5c7e2b3089df170cfbe462fa9400399d751d9c3/lab/tests/optical_discovery_test.c) as C11 and run without arguments. MSVC and [hosted GCC](https://github.com/kuro1337WStuff/hv/actions/runs/45745843636/job/139661575994) passed the discovery sequence and the existing read and capacity controls.

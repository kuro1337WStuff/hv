# 132 · Does the selected Windows Setup image name a CD-ROM driver?

**Yes for the authored optical child, not the disk control.** The controller stayed fixed at `8086:2922`. Two 36-byte SCSI INQUIRY records differed only in byte zero: peripheral type 5 derived `GenCdRom`, while type 0 derived `GenDisk` ([Microsoft identifier table](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/identifiers-for-scsi-devices)). Only the former matched an applicable model in the named optical INF. This is static driver eligibility, not evidence that Windows enumerated hardware, loaded a service or read a disc.

**Source:** the candidate ISO SHA-256 was `a11116c0645d892d6a5a7c585ecc1fa13aa66f8c7cc6b03bf1f27bd16860cc35`. Its `sources/boot.wim` SHA-256 was `cbcca3c293b2dd3ceaf33dc83bde3071fe30cc51ea988bb07efe0dcb98085d68`. The boot header selected index 2; WIM XML identified Microsoft Windows Setup (x64), WindowsPE, WinNT 10.0.19041.1288. Seven-Zip listed and extracted only the two flat published INF/SYS scopes. All 322 INFs and 296 drivers matched the WIM's filenames, sizes and internal SHA-1 values. No image was mounted or modified.

Line 42 of `[cdrom_device.NTamd64]` selects `cdrom_install` for `GenCdRom`. Line 115 of `[cdrom_install.Services]` associates the `cdrom` service (`0x2`) with `[cdrom_ServiceInstallSection]`. Lines 132–136 declare a system-start kernel driver at `%12%\cdrom.sys`; the inventoried file has an AMD64 PE32+ header. The disk arm has no matching generic ID **in this published optical INF**; this says nothing about `disk.inf`. The AHCI controller candidate from [127](127.md) cannot substitute for either child result.

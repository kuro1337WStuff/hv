# 125 · Can the loader exit boot services with yesterday’s memory map?

**No.** In a five-page, guest-owned UEFI map model, allocating one page invalidated the key. `ExitBootServices` rejected the stale key. Reading a fresh map and retrying succeeded exactly once. This is a host model of the interface an OS loader needs, not a call into the workstation's firmware or a Windows Boot Manager trace.

| Operation | Observed result |
|---|---|
| Offer 95 bytes for the original map | Required 96; every buffer and guard byte retained `A5h`. No partial descriptor. |
| Read the original twice | Same key `1`, version 1, two descriptors with **48-byte** stride. A consumer must use the returned stride, not the 40-byte prefix size. |
| Claim `0x101000` as loader data, then repeat the claim | Exactly one conventional page changed owner. The second claim failed. The old key returned `EFI_INVALID_PARAMETER` on exit. |
| Offer the old 96-byte capacity | Required 144; buffer untouched. A fresh read contained one boot-services page at `0x100000`, one loader page at `0x101000` and three conventional pages from `0x102000`, with no new or lost RAM. |
| Exit with the fresh key `2` | `EFI_SUCCESS`. Another map read, allocation and exit were **unavailable**, not EFI error returns. The post-exit read changed neither the supplied size nor any guard. |

Keys `1` and `2` belong to this fixture; callers must treat keys as opaque. After the first failed exit the test used only a map read and exit retry: real firmware can partially shut down services even on that first failed attempt. No runtime services, firmware event callbacks, image dispatch or system table are modeled. See UEFI 2.10 [§7.2.3 GetMemoryMap](https://uefi.org/specs/UEFI/2.10/07_Services_Boot_Services.html#efi-boot-services-getmemorymap) and [§7.4.6 ExitBootServices](https://uefi.org/specs/UEFI/2.10/07_Services_Boot_Services.html#efi-boot-services-exitbootservices).

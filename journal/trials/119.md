# 119 · Can a pending interrupt escape terminal virtual S5?

**No grant or device progress occurred after S5 in the host model.** The test cloned one running platform at PIT tick 8. Its UART transmitter was busy, IRQ0 and IRQ4 were pending (`IRR=11h`), and a cascaded interrupt was in service (`ISR master/slave=04h/02h`). The two copies received different word writes at PM1a control: `3401h` requested S5; `1401h` selected S5 without enabling sleep.

| Observation | S5 requested | Selector only |
|---|---|---|
| First PIC grant, before advancing time | Refused; vector sentinel `ADh` intact | `30h` (already pending) |
| Advance to tick 9, poll UART status, latch PM1 global event | All refused; still tick 8, UART busy, PM1 status `8000h` | New IRQ0 edge, UART drained, IRQ4 asserted, PM1 status `8020h` |
| EOIs, acknowledgments and subsequent grants | No PIC mutation; no vector returned | `30h` (new edge), `39h` (SCI), `34h` (UART); both ISRs ended clear |
| Serial / event / timer programming | Original snapshot unchanged after each attempt; rejected reads preserved their operands | Serial transcript `AB`; timer, event and mask registers remained accessible |

The stopped snapshot was taken **after** the first S5 write. Comparing the entire platform with that snapshot after every refused operation catches side effects that a final interrupt count would miss. The selector-only twin demonstrates that the pending interrupt was deliverable, time could advance, and device events were not vacuous. A wrong sleep type, missing SCI enable, non-word or misaligned control write, and unsupported I/O forms were refused before the split.

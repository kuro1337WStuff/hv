# 135 · Did the optical READ(10) return the installation bytes in order?

**Yes, on the host fixture.** The 10-byte request `28 00 00 03 c5 15 00 00 02 00` returned 4,096 bytes at optical LBAs 247061–247062. All bytes matched an independent read of the image. The cross-sector 64-byte slice also matched the digest established from the **named file** in [trial 134](134.md). Neither Windows nor the hypervisor issued the command.

| Check | Result |
|---|---|
| Full two-sector reply | SHA-256 `f145fbadd6feca0f3bfd7fee4e4f6c67792221604216c1b7aa708cea19c9e28a` |
| Last 16 bytes of the first sector + first 48 of the second | SHA-256 `8d0dd15b53bcd7a6448f5fc564381655a87356b3f19909b3123143b55f0d9461` |
| Byte order and adjacent bytes | The authored C fixture checked both sectors, the literal cross-boundary sequence, both adjacent bytes and output guard bytes. |
| Invalid requests | Wrong opcode, malformed CDB, oversized or out-of-media transfer, or a short output buffer: zero backing calls and unchanged output. A valid request with an unavailable backing made one lookup and no copy. |

The local replay verified the full SHA-256 of the pinned ISO **before** invoking the reader. It also checked trial 134's distinct one-block-shift digest. [Machine-readable replay receipt](../reports/optical-read10-135.receipt.json) · [independent input witness](../reports/install-content-134.witness.json). No installation bytes were published.

The fixture follows the [pinned EDK II CDB builder](https://github.com/tianocore/edk2/blob/556dcfb466e9f05affeaff881d738807f8156d3c/MdePkg/Library/UefiScsiLib/UefiScsiLib.c#L946-L960): big-endian starting LBA at byte 2 and transfer count at byte 7. It supports only a plain READ(10), at most two 2,048-byte blocks. It does not advertise media geometry, implement sense reporting, transfer guest memory, model AHCI/ATAPI transport, or establish post-firmware optical access.

# 108 · Can the reader select the EFI file without touching the BIOS image?

**PASS · host-only, in memory.** The selector recovered all seven marker bytes `48 56 00 EF FF 33 12` from `\EFI\BOOT\BOOTX64.EFI` on a synthetic disc. The first catalog entry points at a BIOS decoy. Changing just the EFI section's platform byte from `EF` to `00` caused refusal after the catalog: neither boot image was read.

| Input | Optical LBAs read, in order | Result |
|---|---|---|
| BIOS default + final EFI section | `17,19,28,29,30,31` | EFI extent `[28,32)`; seven bytes from block 31, offset 1536. |
| Same disc, EFI platform byte changed | `17,19` | No image selected; output unchanged. |
| EFI extent relocated to end of disc, different file | `17,19,32,33,34,35` | Three new bytes `FA 00 39` from block 35, offset 1536. |

Addresses in the read trace are **2,048-byte optical blocks**. The catalog's 16 image sectors are **512 bytes each**: four optical blocks, not sixteen. The reader checks the catalog validation entry, disjoint declared extents, the fixture's FAT12 geometry and single-cluster directory path. The control rejects a wrong directory or filename, repeated or bad clusters, overlapping or out-of-range images, and a short or refused read at each step. It compares the whole disc before and after every case and, on failure, compares the whole output with the original.

**Reproduce** in an x64 MSVC developer shell at [feature revision `fcc197ec`](https://github.com/kuro1337WStuff/hv/tree/fcc197ec92d8fadee68e71eb2cf07ea4318630f9):

```bat
cl /nologo /O2 /std:c11 /TC /W4 /WX lab\tests\optical_select_test.c /Fe:optical_select_test.exe
optical_select_test.exe
```

The control exited successfully on the linked feature tree `33b169758743168e929f129548e40df9a16ea0eb`. This is a fixed-profile selector, not a general optical driver: the marker is **not** an executable, the installer ISO was **not** used for this test, and no VM was started.
